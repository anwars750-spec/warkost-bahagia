# V1.7B — Supabase Integration Foundation

## Goal

Connect the Flask application to the existing Supabase server-side business layer without changing the Customer V1.6 runtime by default.

## Safety rule

`WARKOST_BACKEND` defaults to `sqlite`.

That means the existing Customer V1.6 flow remains unchanged until the Supabase backend is explicitly enabled on the server.

## Server-side gateway

`app/supabase_gateway.py` provides:

- `server_customer_delivery_quote`
- `server_customer_delivery_order`
- backend/configuration status

The gateway uses the Supabase service-role key only on the Flask server.

The service-role key must never be:

- placed in HTML
- placed in JavaScript
- returned by an API
- committed to Git

## Current scope

V1.7B-01 is intentionally limited to the integration boundary.

We have **not** switched the customer checkout to Supabase yet.

Reason: the existing local checkout includes voucher behavior and SQLite identity, while the Supabase customer-order RPC currently covers server-side product pricing and delivery calculation but does not yet reproduce the local voucher claim flow. Switching immediately would therefore risk breaking the 13/13 Customer V1.6 contract.

## V1.7B-02 — Identity Bridge

A migration-safe identity bridge is now in place.

- SQLite `users.supabase_user_id` stores the mapped Supabase Auth/profile UUID.
- Supabase `profiles.legacy_user_id` stores the legacy SQLite `users.id` during migration.
- A unique constraint/index exists on both sides to prevent one identity from being mapped to multiple local users.
- `/api/system/identity` exposes only the current user's mapping state.
- `/api/admin/supabase/identity` allows Admin/Owner to link an existing local account to an existing Supabase profile after role validation.
- The service-role key remains server-only.
- No automatic email-based linking is performed yet; explicit mapping avoids accidental account takeover during migration.

No customer UI or default checkout behavior was changed.

## Next integration step

Before enabling the Supabase order path:

1. establish the order ID / customer UI contract
2. add a feature-flagged order path using the identity bridge and V2 promotion-aware RPC
3. run the existing 13-step Customer V1.6 regression
4. only then enable Supabase ordering for the operational E2E

## V1.7B-03 — Voucher / Promotion Parity

Supabase now has a server-side promotion foundation covering the critical Customer V1.6 voucher contract:

- promotion code, type, value, minimum order, maximum discount, quota, validity window, active state
- one claim per customer per promotion
- claim validation before checkout
- server-side discount calculation
- server-side order total calculation includes the discount
- service-role-only wrappers for the Flask integration gateway
- server_customer_delivery_order_v2 accepts an optional promo code

The existing V1.6 SQLite checkout remains unchanged. The new Supabase promotion path is NOT enabled by default.

Admin campaign-management UI and automatic migration of existing SQLite promotion records remain separate tasks. They are intentionally outside the first checkout cutover.

## V1.7B-04 — Order ID Contract

The order identifier boundary is now explicit before any checkout cutover.

- Customer UI keeps an app-facing integer `order_id` contract.
- Supabase keeps the operational UUID order id as `supabase_order_id`.
- SQLite `supabase_order_links` stores only the bridge metadata; it does not duplicate order items, payment, stock, fulfillment, delivery, sales, or loyalty state.
- Human-readable `order_no` remains the stable customer-facing order reference.
- `app/order_contract.py` centralizes normalization and bridge resolution.
- `app/supabase_gateway.py` can read a customer-owned Supabase order and its immutable item snapshots through the server-only gateway.
- `/api/system/order-contract` exposes the contract version/status to an authenticated session.
- `/api/customer/supabase-order/<bridge_id>` is an adapter endpoint for future feature-flagged UI use.

### Safety boundary

V1.7B-04 does **not** switch checkout, payment, or customer order history to Supabase.

The existing V1.6 SQLite path therefore remains the regression baseline. The bridge exists so V1.7B-05 can switch one path at a time without forcing the frontend to understand Supabase UUIDs.


## V1.7B-05 — Feature-Flagged Supabase Order Path

The customer `/api/order` route now branches only when `WARKOST_BACKEND=supabase`.

Supabase mode:
1. requires an explicit SQLite→Supabase identity mapping
2. validates and normalizes the cart server-side
3. calls the promotion-aware `server_customer_delivery_order_v2`
4. reads the created order back from Supabase
5. creates only a local bridge reference
6. returns the existing customer-facing order contract plus `backend=supabase`

SQLite mode is unchanged.

### Payment boundary

Supabase orders remain `payment_pending` at this milestone. The existing SQLite demo-payment endpoint is deliberately not used for Supabase orders.

This is intentional: payment verification must be connected to the Supabase payment state machine before the full 13-step Customer V1.6 flow can be called equivalent in Supabase mode.

### Fail-closed rule

If the Supabase order request has an unknown outcome or the order cannot be read back, the Flask route returns an error and does **not** fall back to SQLite. This prevents accidental duplicate orders.
